## 已知事实与判断范围

## 确认的代码问题

1. **预签到页面解析过于严格。** 原版 `parseStatusPage` 只接受扁平 `primaryAttend` 对象或 `signstatus = 数字`；嵌套对象、带引号的 `signstatus` 或没有这些标记的页面会报错。移动端在调用提交接口之前先核查状态，因此解析失败可以直接阻止签到。
2. **未知数值被视作未签到。** 原版将成功状态集合之外的任意整数都当作 `READY`，包括未知状态；这不能作为允许提交的依据。
3. **执行结束被展示为任务完成。** 所有账号尝试结束会将任务置为 `DONE`，界面直接显示“任务已完成”，即使实际账号失败。`DONE` 只表示执行结束，不能代表签到成功。
4. **重复核查可能覆盖已确认的成功。** 提供者已经返回经远端确认的 `SIGNED` 后，移动端仍再次请求状态；后一次网络或解析错误可能把成功覆盖为失败。

## 已实施修复

- 支持嵌套状态对象和字符串数字；未知状态继续报错，不直接放行。
- 当课程预签到页面缺少状态标记时，使用同一会话读取课程活动列表，按课程、班级及活动 ID 刷新活动上下文和判断是否截止。列表的 `userStatus` 不作为个人签到成功的证据。
- 必要时刷新列表中的 `ext`，重新读取预签到页。登录过期、未知状态、目标不存在仍明确报错。
- 提交响应为 `success` 时，仍需读取该账号在目标活动中的个人签到结果；仍未签到则展示失败。
- 保留已确认的成功，避免重复核查覆盖；失败任务显示“签到未完成”或“部分账号签到失败”。提交前失败明确提示“未提交”。

## 签到请求流程改进（2026-10-10）

按用户要求修复重复检查、错误原因丢失和提交计数三个问题；验证码接续不在本次范围内。

- 新任务由提供者 `submit` 统一执行：个人状态查询 → 活动详情 → `analysis` → `analysis2` → `stuSignajax` → 个人结果核验。正常路径提交前 `preSign` 从 3 次降为 1 次、详情从 2 次降为 1 次、上下文从 2 组降为 1 组。同一次提交复用同一请求会话以及预签到、详情接口返回的 Cookie。
- 移除独立 `preflight` 接口和任务层的重复核验。恢复已有提交记录的任务，以及真正提交后的超时，仍单独核查远端以决定是否重试。准备阶段超时不伪装为提交超时。
- `ext` 刷新后在该次请求上下文中复用，后续核验不重复刷新旧 `ext`，也不直接修改课程缓存对象。
- 未知签到响应保留服务端文本或 JSON 中的 `errorMsg/msg/message`；HTTP 失败同时展示状态码和服务端说明。展示文本去掉 HTML 脚本、样式和标签，并限制 400 字符，完整页面不直接塞入结果卡。
- 计数由实际 `stuSignajax` 请求的发送通知触发，不再在进入提交函数时计数。准备失败、已签到、截止、等待人脸/验证码、二维码失效及发送前取消均计为 0；请求已开始但服务端拒绝或超时仍计为 1。计数表示发起提交请求的次数，不代表服务端接受次数。
- 90 项测试、类型检查、差异空白检查通过。新增协议回归覆盖正常调用序列、Cookie 复用、准备失败零提交、超时计数、具体失败原因和旧 `ext` 刷新复用。
